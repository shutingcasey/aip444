# Failure Analysis & Overall Observations

## Failure 1: `pdf-parse` corrupts state when the same PDF is parsed twice in one process

**What happened:** Phase 3 originally called `extractDocumentText()` twice per run — once inside the reused Phase 1 extraction logic, and once more directly in `phase3/cli.ts` to get the raw posting text for the legitimacy agent (which needs to scan for contact emails/payment requests that the structured `JobPosting` schema doesn't capture). The second parse of the *same file* intermittently failed with `bad XRef entry`, even though the first parse of that exact file succeeded moments earlier.

**Why:** Isolated testing showed a single `require("pdf-parse")` instance reused across two sequential calls parses the same buffer fine twice, but the pattern originally used in `document.ts` — `const pdfParse = (await import("pdf-parse")).default` re-executed inside the function on every call — reliably reproduced the corruption on the second call, with or without a delay in between. `pdf-parse` bundles an older, vendored copy of `pdf.js` that appears to hold mutable global/module state that isn't safely reentrant across that particular import pattern. This was never something the assignment schema/prompt could catch — it's a library-level state bug that only appears when the same document is parsed more than once in a single process, an edge case that unit-testing a single extraction call would never surface.

**Fix:** Switched `document.ts` to import `pdf-parse` and `mammoth` once at module scope (static imports) instead of dynamically inside the function on every call. More importantly, refactored `extractJobPostingData()` (`src/phase1/extractJob.ts`) to return the raw extracted text alongside the structured record, so Phase 3 reuses that text instead of re-parsing the file at all. This is strictly better regardless of the underlying library bug — it avoids redundant work and removes an entire class of "parse the same file twice" risk by construction, rather than papering over the specific error.

**What I'd change with more time:** File an issue against `pdf-parse` (it's a thin, mostly-unmaintained wrapper around an old `pdf.js`) or migrate to a more actively maintained PDF text extraction library. For this assignment, avoiding double-parsing was the pragmatic fix and is arguably better architecture anyway.

## Failure 2: Canva-exported resume PDFs have no extractable text layer

**What happened:** The first resume PDF provided (exported from Canva) parsed to just 2 characters of whitespace — `extractDocumentText()` correctly detected this (empty-text check) and threw a clear error rather than silently producing an empty/hallucinated resume, but Phase 2 was still blocked until a usable file was provided.

**Why:** Some design tools (Canva confirmed here) render certain fonts as vector path outlines on PDF export rather than embedding a real text layer with a ToUnicode CMap. Both `pdf-parse` (older bundled `pdf.js`) and a directly-installed current `pdfjs-dist` were tested against the same file and both returned empty text — this ruled out "just use a better library" as a fix. Visually the PDF looks completely normal; there is no way to detect this without attempting extraction (the metadata reports `Creator: Canva` but plenty of legitimate Canva PDFs export fine, so `Creator` alone isn't a reliable signal to warn on preemptively).

**Fix / mitigation:** This is a genuine input limitation, not a bug in this system — the safety/reliability requirement here is to fail loudly and specifically rather than crash or hallucinate. `extractDocumentText()` throws `"...contained no extractable text (it may be a scanned image)"`, the CLI catches it and exits with that message rather than corrupting `data/resume/resume.json`, and the README documents the workaround (re-save as `.docx`, or OCR-import via Google Drive). The candidate re-exported the same resume from Canva a second time (still Canva, but this export did embed real text — Canva's behavior here is apparently inconsistent depending on template/font choices) and the second file parsed cleanly.

**What I'd change with more time:** Add an OCR fallback (e.g. render page → image → Tesseract) that only triggers when direct text extraction returns empty, so scanned/outlined PDFs degrade to OCR instead of hard-failing. Skipped for this assignment to keep the dependency footprint small and because the actual failure was rare (1 of 9 total PDFs processed across the whole project).

## Other weaknesses observed (not blocking, but worth noting)

- **Required vs. preferred skill classification is not fully reliable** when a posting mentions the same skill in two places with conflicting framing (see `eval/extraction-spot-check.md`, ATS Automation posting: LabVIEW/Python appear once unqualified and once explicitly "preferred experience" — the model picked required). Low-severity since it's a genuinely ambiguous source text, not a clean miss, but it means `topRequiredSkills` in the market analysis could be mildly skewed if this pattern is common across a larger corpus.
- **Seniority level is not always inferred from the job title** even when unambiguous (`"Senior Software Developer"` → `experience.seniorityLevel: null` instead of `"Senior"`). The prompt asks for seniority "as implied by the posting" but the model appears to weight explicit "Level:" fields over titles. Cheap fix: add an explicit instruction/example to infer seniority from common title prefixes (Senior/Staff/Principal/Lead/Junior) when no separate level field exists — not yet applied, since it was caught late in the spot-check.
- **Fit scoring doesn't factor in the legitimacy verdict** — a fake posting with no real requirements can score a high fit percentage, since the two agents run independently and fit scoring only looks at requirement-to-resume matching. Mitigated at the report layer (legitimacy banner is placed first, in red, above the fit score) rather than by suppressing the fit section, per the assignment's own instruction that "the remaining sections should still be generated... the analysis is still useful."
- **Small run-to-run score variance** (63% vs. 60% on an identical rerun) — expected LLM sampling variance, does not change recommendation labels in testing, see `eval/scoring-check.md`.

## Overall summary

Across 8 market postings + 2 additional Phase 3 test postings + 1 synthetic scam posting (11 total LLM-driven extractions/assessments), the system produced zero hallucinated required fields, correctly used `null`/"not listed" when data was genuinely absent, and correctly identified both a legitimate and a fraudulent posting with accurate, independently-verifiable evidence for every signal cited. The two failures found were an environment-level library bug (fixed) and an input-format edge case (handled gracefully, not silently). The two soft weaknesses (required/preferred ambiguity, seniority-from-title) are minor and specific to ambiguous source text rather than systemic hallucination.

**Would I trust this in a real job search?** For the structured extraction and market analysis, yes, with light spot-checking — the numbers are grounded in deterministic code, not LLM arithmetic, and the qualitative synthesis stayed consistent with the underlying data across all runs. For the fit score and legitimacy verdict specifically, I'd treat them as a strong first-pass filter and conversation-starter rather than a final answer — I would always personally re-verify a RED/YELLOW legitimacy verdict's underlying evidence before deciding whether to apply (which the report already surfaces, since every signal comes with cited evidence, not just a bare label), and I would not skip applying to a role solely because of a low fit score, which is exactly the behavior the scoring bands are designed to prevent.
